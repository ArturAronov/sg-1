# SG-1 AWS IAM reference

This is the permissions companion to the [LLM setup runbook](../docs/SETUP.md). It distinguishes **the privileges used to build infrastructure** from **the privileges granted to SG-1 at runtime**. Never solve a runtime denial by attaching the provisioning role to EC2 or Fargate.

Sources of truth: [`iam.tf`](../iam.tf), [`malware.tf`](../malware.tf), [`versions.tf`](../versions.tf), [`aws.go`](../../../sg-1/backend/internal/platform/aws.go), and [`scripts/aws`](../../../scripts/aws/). Re-read them if the revision changes.

Current deployment defaults: Entra only (`enable_onelogin=false`), one public `chickensoup.dev` zone for platform and wildcard-app records. In the capability tables below, references to two IdP secrets/two public zones describe the optional expanded configuration: grant access only to the enabled provider's secret and actual zone(s). Do not provision a OneLogin secret or authorize a second zone unless explicitly enabled/selected.

## ARN notation

The examples use commercial partition `arn:aws`. Replace all placeholders privately before policy validation. Secret names acquire an AWS-generated suffix: use exact returned ARNs where possible, not guessed ARNs.

| Symbol                | Meaning                                                          |
| --------------------- | ---------------------------------------------------------------- |
| `A`, `R`, `P`         | Account ID, region, deployment name (`sg1-prod` by default)      |
| `B`                   | Application bucket `P-A-R`                                       |
| `PROJECT`             | Project UUID; not a user-supplied arbitrary role/repository name |
| Platform repositories | `arn:aws:ecr:R:A:repository/P-api` and `.../P-web`               |
| Project repositories  | `arn:aws:ecr:R:A:repository/P-project-*`                         |
| Build roles           | `arn:aws:iam::A:role/P-build-*`                                  |
| Build boundary        | `arn:aws:iam::A:policy/P-build-boundary`                         |
| Workload secrets      | `arn:aws:secretsmanager:R:A:secret:P/workloads/*`                |
| Application settings  | Exact ARN of `P/config/application`                              |

An identity Allow is insufficient if an SCP, session policy, permissions boundary, resource policy, endpoint policy, KMS key policy, or explicit Deny blocks the request. Cross-account access needs both sides. Tags are ownership metadata, **not** a universal authorization boundary in the current implementation.

## 1. Human/automation identities

| Identity                             | Intended privileges                                                                                                 | Must not be reused as                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Prerequisite/bootstrap administrator | Approved VPC/NAT/state/hosted-zone/IdP/role creation outside this module                                            | Application runtime or routine publisher                                  |
| Terraform provisioning role          | Scoped resource lifecycle for this module, backend access, read two IdP secrets                                     | EC2 instance profile, CodeBuild service role, or Fargate role             |
| Release publisher                    | Push/pull/inspect only the two platform ECR repositories; upload only `releases/*`                                  | Provisioner, secret operator, or SSM administrator                        |
| Read-only validator                  | Metadata and sanitized health/policy inspection                                                                     | Secret reader or resource creator                                         |
| Secret-bootstrap operator            | Read relevant metadata; approved initialization/update of specific IdP/settings secrets; scoped Cognito user lookup | Shared application user or general purpose CI role                        |
| SSM host operator                    | Approved sessions on the specific EC2 instance                                                                      | Unprivileged app operator: SSM/root access is a platform-admin capability |

Use IAM Identity Center or federation with short sessions, approved trust, MFA where applicable and auditable session identity. Do not invent a trusted AWS principal, GitHub OIDC subject, external ID, or organization ID. A GitHub OIDC publisher trust, if approved, must constrain both `aud=sts.amazonaws.com` and `sub` to the exact repository and protected branch/environment; this repository's validation workflow does not currently deploy to AWS.

### Terraform backend permissions

Use [the exact-key state policy example](policies/terraform-state.json.example) for the **default workspace**. It provides:

- `s3:ListBucket` limited by `s3:prefix` to the configured state key and lock key.
- `s3:GetObject`, `s3:PutObject` on the state object.
- `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` on `<STATE_KEY>.tflock`.
- No state-object deletion, bucket management, public access, or application-bucket access.

Additional Terraform workspaces use different keys; do not silently broaden the policy. Native locking requires Terraform >=1.10. This module uses S3 locking, not a DynamoDB table.

Policy files are templates, not live-account-tested grants. If the Terraform version enumerates workspace prefixes during initialization, inspect the exact denied `ListBucket` prefix and request only the necessary discovery-prefix addition (for example the configured `workspace_key_prefix/`); do not grant access to other state objects or remove the prefix condition wholesale. Review bucket/key naming, any existing bucket policy and the actual backend requests before attaching.

For a customer-managed state KMS key, request `kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey`, and any required key discovery (`kms:DescribeKey`) on the **exact** key; authorize the role in the key policy too. Restrict use through S3/encryption context where supported and verify against the actual backend configuration. Do not grant `kms:*` or key administration to the publisher/runtime.

### Terraform provisioning capability map

**This is a review checklist, not an account-tested, attach-and-forget policy.** AWS create/tag/read operations have different resource/condition support, and the pinned provider may make extra read calls. Do not automatically attach broad AWS managed FullAccess policies.

Use named SG/VPC/subnet/hosted-zone/secret resources where supported; for creation before an ARN exists use supported region, VPC, request-tag and name conditions. ### Publisher permissions

[publisher.json.example](policies/publisher.json.example) covers `scripts/aws/publish.sh` and Buildx access to the two **existing** platform repositories:

- `ecr:GetAuthorizationToken` on `*` (the API does not support repository resource scope).
- Push/pull layer and manifest APIs, `DescribeImages`, `DescribeImageScanFindings` on only `P-api` and `P-web`.
- `s3:PutObject` and multipart cleanup on only `B/releases/*`.
- No IAM, ECS deployment, SSM, secret read, upload/build-source access, repository creation, or image deletion.

The script reuses existing immutable tags; a push-denial is not permission to delete/re-tag an existing release. Public base-image downloads additionally require network access and may be subject to Docker Hub limits. The publisher template intentionally does **not** include `check.sh` permissions. Keep a separate validator role or explicitly review that additional read-only scope.

### Read-only validation permissions

For the existing `check.sh`, authorize:

| `s3:GetBucketPublicAccessBlock`, `s3:GetEncryptionConfiguration`, `s3:GetBucketVersioning` | Exact `B` bucket ARN                                                                                                        |
| `rds:DescribeDBInstances`                                                                  | Approved RDS instances where supported; scope region/discovery separately if necessary                                      |
| `cognito-idp:DescribeUserPoolClient`                                                       | Exact employee user-pool ARN; response contains a client secret, so use the script's projection, never display raw response |
| `ec2:DescribeInstances`                                                                    | Discovery requires `Resource: "*"`; restrict region and intended use                                                        |

Additional review commands need specific read actions: `ec2:DescribeSecurityGroups`, `DescribeSecurityGroupRules`, `DescribeVpcAttribute`, `DescribeSubnets`, `DescribeRouteTables`, `DescribeVpcEndpoints`, `DescribeNetworkAcls`; ELB `Describe*` for the inspected resources; `guardduty:GetMalwareProtectionPlan`/`ListMalwareProtectionPlans`; `ecr:GetRegistryScanningConfiguration`; IAM `GetRole`, `GetRolePolicy`, `ListRolePolicies`, `ListAttachedRolePolicies`, `GetPolicy`, `GetPolicyVersion`; scoped `access-analyzer:ValidatePolicy` and approved CloudTrail lookups. Grant only what the chosen checks need. Reading S3 objects, secrets, logs, state, or Cognito users is **not** implied by the phrase "read-only".

### SSM human access

Authorize `ssm:StartSession` only on the approved EC2 instance ARN and the approved Session document (commonly `arn:aws:ssm:R::document/SSM-SessionManagerRunShell`; verify the actual document). Add the client's required `ssmmessages:OpenDataChannel` and `ssm:ResumeSession`/`TerminateSession` only for sessions owned by that identity, using your organization's principal/session ownership convention. Do not use a guessed `${aws:username}` condition for a federated identity. `ssm:DescribeInstanceInformation` and `ec2:DescribeInstances` can support discovery.

Do not grant `ssm:SendCommand` unless approved; Run Command can execute privileged commands and has separate instance/document scope. Review Session Manager logging/encryption configuration with the platform owner; this module does not configure session audit logging. All approved host operators must be treated as privileged secret administrators.

The current controller does not have broad project IAM-role/CodeBuild-project/ECR deletion permissions. Project retirement and history/image retention need an explicit operator process, not newly granted wildcard cleanup permissions.

## 3. Per-project CodeBuild roles and boundary

Created dynamically by `AWSRuntime.PrepareNetwork`, not `terraform apply`.

**Role:** `P-build-PROJECT`. **Trust:** `codebuild.amazonaws.com`, `sts:AssumeRole`, with both:

```text
aws:SourceAccount = A
aws:SourceArn = arn:aws:codebuild:R:A:project/P-PROJECT
```

It must carry the `sg1-project=PROJECT` tag and the exact `P-build-boundary` permissions boundary. The worker checks ownership and boundary before using an existing role.

| Effective inline Allow                                                                                                                                    | Scope                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `s3:GetObject`                                                                                                                                            | `arn:aws:s3:::B/builds/PROJECT/*`    |
| `ecr:GetAuthorizationToken`                                                                                                                               | `*`                                  |
| `ecr:BatchCheckLayerAvailability`, `GetDownloadUrlForLayer`, `BatchGetImage`, `InitiateLayerUpload`, `UploadLayerPart`, `CompleteLayerUpload`, `PutImage` | Exact `P-project-PROJECT` repository |
| `logs:CreateLogStream`, `logs:PutLogEvents`                                                                                                               | `/aws/codebuild/P` streams           |

The boundary permits the same action families across `builds/*` and `P-project-*`; the per-project inline policy narrows them to one UUID. **A boundary does not grant permissions on its own.** Do not expand the inline policy to the entire boundary scope. No database/provider/settings secrets, S3 upload read/write, arbitrary IAM, or cross-project ECR push is granted.

Generated builds execute untrusted source with CodeBuild privileged Docker enabled; this is **not** privileged Docker on EC2. The CodeBuild role's temporary scoped AWS credentials are part of that build's exposure. Never claim that the build has no credentials; its safety relies on its narrow role, boundary and isolated service. CodeBuild currently has no VPC configuration here; Fargate network restrictions do not apply to builds. Assess outbound build traffic, dependency supply chain, log contents and build credential abuse before acceptance.

## 4. ECS execution role versus task role

**Execution role:** `P-task-execution`. **Trust:** `ecs-tasks.amazonaws.com`, `sts:AssumeRole`, `aws:SourceAccount=A`.

| Actions                                                                      | Scope                                                           |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `ecr:GetAuthorizationToken`                                                  | `*`                                                             |
| `ecr:BatchCheckLayerAvailability`, `GetDownloadUrlForLayer`, `BatchGetImage` | Project repositories plus `P-api` trusted init image repository |
| `logs:CreateLogStream`, `logs:PutLogEvents`                                  | `/aws/ecs/P` streams                                            |
| `secretsmanager:GetSecretValue`                                              | `P/workloads/*`                                                 |

ECS uses this shared execution role to pull images, create logs and inject the specific `DATABASE_URL` secret ARN in each task definition. The role can access all workload-secret ARNs; the trusted controller controls which one is referenced. It is **not** a per-project IAM execution role.

**Task role:** none (`TaskRoleArn` absent). Generated app processes receive no AWS task-role credentials. They receive their own DB credential as an environment secret; assume generated code can read/exfiltrate its own data/credential within its permitted egress. Do not add `taskRoleArn`, enable ECS Exec, grant S3 permissions, or inject provider credentials to make an app start.

| `events:PutRule`, `DeleteRule`, `PutTargets`, `RemoveTargets`, `DescribeRule`                                                    | `arn:aws:events:R:A:rule/DO-NOT-DELETE-AmazonGuardDutyMalwareProtectionS3*` |
| `s3:GetBucketNotification`, `PutBucketNotification`, `ListBucket`                                                                | `B`                                                                         |
| `s3:GetObject`, `GetObjectVersion`, `GetObjectTagging`, `GetObjectVersionTagging`, `PutObjectTagging`, `PutObjectVersionTagging` | `B/uploads/*`                                                               |
| `s3:PutObject`                                                                                                                   | `B/malware-protection-resource-validation-object`                           |

The bucket TLS Deny applies to everybody. The upload quarantine Deny exempts only this scanner role so it can read unscanned input. The EC2 role lacks `s3:PutObjectTagging`; do not give it permission to manufacture clean-scan status. Adding a different encryption scheme/KMS key or changing prefix/tagging requires updating all applicable role, key, bucket and endpoint policies together.

## 6. Database privileges are separate from IAM

Current RDS connections use password authentication and verified TLS, **not IAM DB authentication**. `rds-db:connect` will not fix a PostgreSQL login, CA, ownership, or SQL permission failure.

| SQL principal / secret           | Intended privileges / exposure                                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Control RDS `sg1admin`           | RDS-managed admin; temporary `.env.migrate`; migrations own schema; host role can retrieve master secret                                                                                    |
| Control `sg1_api`                | `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`; connect to `sg1`, schema USAGE, table DML, sequence usage/select and default grants; no normal migration/role creation authority |
| Application RDS `sg1admin`       | Worker provisioner credential in `.env.worker`; creates separate project preview/production roles/databases; trusted and privileged                                                         |
| Project preview/production roles | Separate generated passwords/DB ownership, non-superuser, no create-role/create-db/replication; AWS path adds connection limit 10; DB access revoked from PUBLIC                            |

All production connections use `sslmode=verify-full` with the official RDS CA. `configure.py grant` revokes PUBLIC control DB connection/schema creation and application provisioner DB connection as coded. A shared application RDS server/SG is not per-project network isolation: PostgreSQL credentials/privileges enforce the cross-project boundary. Test actual PostgreSQL 17 ownership/role behavior with the DBA rather than promising it from IAM checks.

## 7. Diagnosing AccessDenied

1. Identify the caller and operation without printing secrets. Record action, resource ARN, region, request ID and redacted error; don't dump entire SDK/HTTP responses.
2. Locate the authoritative policy: Terraform provisioning identity, publisher, validator, `P-control`, `P-build-PROJECT`, ECS execution, GuardDuty, or SSM human. AWS service calls are not all made by the EC2 role.
3. Check trust/SourceArn/SourceAccount, PassRole service condition, identity policy, permissions boundary/session policy/SCP, resource policy, endpoint policy and KMS key policy. SG/TLS/DNS failures are not fixed with IAM.
4. Review sanitized CloudTrail events with approved audit permissions. `iam:SimulatePrincipalPolicy` is optional and does not prove the real environment's resource policies/SCPs/conditions or service behavior.
5. Validate a proposed policy with `aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY --policy-document file://<rendered-private-policy.json>` (resource policies require their appropriate type/context). Resolve unsupported actions/conditions before attaching. ValidatePolicy checks policy semantics; it does not certify least privilege or authorize deployment.
6. Present the narrow change and blast radius for approval; update the correct IaC/dynamic policy generator, re-plan/redeploy as needed, then rerun the failed check. Never attach `AdministratorAccess` or open arbitrary egress to find out whether it works.

For published IAM action/resource support, use the [AWS Service Authorization Reference](https://docs.aws.amazon.com/service-authorization/latest/reference/reference_policies_actions-resources-contextkeys.html), [Terraform S3 backend permissions](https://developer.hashicorp.com/terraform/language/backend/s3#permissions-required), and [ALB Cognito requirements](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html). AWS policies and provider behavior can evolve; verify against the actual region/account and locked provider.
